## Interfaces

All feature interfaces are **HTTP**. Background execution is internal, not a new public message, stream or RPC API. There is no public provider callback, retry or cancellation endpoint. The following shared schema and rules are normative for each changed HTTP operation.

### Shared report and lifecycle representation

**ASOR-CT01.** Existing `status` remains the report workflow status, never the AI job state. Allowed current values are `awaiting-review`, `resubmitted`, `awaiting-citizen-info`, `ai-screened-out`, `approved`, `rejected`. Existing historical `submitted` and `screening` rows remain readable with their original status/timeline, treated as open; new operations do not emit those statuses. Unknown historical statuses are displayed verbatim, labelled legacy, and remain officer-openable; `open` includes every nonfinal status. No legacy row is automatically sent to any provider on upgrade.

Every citizen/officer report list item retains its baseline keys and adds the **Summary** fields below. Both detail routes retain their baseline keys and add the **Detail** fields. Create/recovery/decision responses retain route-specific base fields and add Summary. All new fields are always present; nullable means JSON null, never omitted or empty string as a null substitute.

| Field | Shape and semantics |
| --- | --- |
| `revision` | Positive integer; starts at 1 for a new report. Increments once per committed citizen/officer workflow mutation. AI-only progress/results do not increment it. Legacy rows start at 1 on exposure. |
| `evidence_revision` | Positive integer; starts at 1, increments once when clarification/resubmission appends evidence. Immutable evidence membership within a revision. |
| `intake` | `{state,reason,assessment_id}`. `state` is `open` or `screened-out`; reason string and assessment ID are null unless a currently effective screen-out exists. A historical AI screen-out remains in assessment history after recovery/override. |
| `officer_decision` | Null until human action, else `{action,officer_id,reason,created_at,event_id}`. Action `approve`, `reject`, `request-info`; reason string or null. Request-info is not a final decision. Existing legacy officer events may have `officer_id:null`; new authenticated actor IDs are recorded, or `reviewer-token` for the preserved shared-token path. |
| `manual_review` | `{requested:boolean,requested_at:timestamp-or-null,reason:string-or-null}`. Once requested, marker persists for history; active manual queue requires open claim. No separate appeal ID. |
| `ai` | Summary object below. Present for every row, including legacy rows without an assessment. |
| `provisional_points` | Existing integer report points, 0 for newly created/unapproved claims; 2/3/3 only on officer approval. Preserve old stored values. Never model-set. Added to officer detail (citizen detail/list already expose it). |
| Detail `assessment` | Current validated assessment for the current evidence revision, or null; may remain null at technical failure. |
| Detail `assessment_history` | Array of all accepted earlier assessments, oldest first by completion then ID. Includes screen-out explanation after manual review or resubmission. Empty `[]` when none. |
| Detail `timeline` | Existing event keys `id,event_type,actor,old_status,new_status,created_at,reason`; officer detail gains the same timeline. Old values remain. New workflow mutations append exactly one event, not one per replay. |
| Detail `media` | Existing `url,filename,mime_type,type` plus `media_id,resource_name,file_size,sha256_hash,evidence_revision`. filename is original display name; resource_name is canonical server-assigned route basename; url is authoritative for fetching. Original submitted order, then appended evidence order; no storage paths or provider URI. Legacy metadata unavailable becomes null for added fields only except resource_name, resolved from its safe existing basename. |

AI Summary shape: `{job_id,state,outcome,recommendation,attempt_count,max_attempts,failure_code,failure_reason,next_attempt_at,started_at,completed_at,processing_ms,assessment_id,evidence_revision,late_result}`. `state` enum: `not-requested`, `pending`, `running`, `retry-wait`, `completed`, `failed`, `cancelled`. `outcome` null except completed: `relevant`, `irrelevant`, `uncertain`. Recommendation null except completed: `recommend-approve`, `recommend-reject`, `needs-human-judgment`, `screen-out-irrelevant`. `attempt_count` integer 0–3, `max_attempts:3`; elapsed `processing_ms` nonnegative integer milliseconds or null before any completed attempt. IDs/times/failure details nullable when unavailable; `evidence_revision` current job revision or null if not requested. `late_result` boolean defaults false. `not-requested` has null job/result/times/failure, count 0, no automatic job. Officer Detail `ai` additionally exposes `attempts`, `elapsed_ms`, and current-job aggregate `usage,cost,billing_state` per Operational visibility and Usage; top-level officer detail additionally exposes `usage_history`. Arrays are empty for no job, aggregate usage/cost are unavailable, billing_state not-dispatched, and elapsed_ms null. Citizen detail uses AI Summary without operational-only additions.

**ASOR-CT02.** Status transitions and authority:

| Trigger | Result | Invariants |
| --- | --- | --- |
| Accepted new report | `awaiting-review`, intake open, AI pending | Report, evidence association, initial event and job are durable together; points 0. Officer may act immediately. |
| Valid current-job clear irrelevance, no intervening workflow action | `ai-screened-out`, intake screened-out | AI intake action only; `officer_decision:null`; points unchanged at 0. |
| Relevant/uncertain/completed or failed AI | Workflow unchanged | All eligible open claims remain officer-reviewable; no AI rejection or award. |
| Officer approve/reject | `approved` / `rejected`, intake open | Terminal human workflow; points mapping/0 respectively for new claims. No automatic reversal, duplicate award or finalization by AI. |
| Officer request-info | `awaiting-citizen-info`, intake open | Not terminal; reason visible to citizen; AI cannot override the officer's requested-information workflow. |
| Citizen manual review of screen-out | `awaiting-review`, intake open, manual marker true | Same ID/evidence/explanation; no new AI job and no repeat automatic screen-out. |
| Citizen resubmit of screen-out / clarification response | `resubmitted`, intake open, new evidence revision and job | Same ID, append evidence and retain all earlier evidence/explanations/events; no reset of past job accounting. |

Officer workflow mutations and manual-review requests take precedence over AI automation for that evidence revision. A result completing after such a mutation may populate advisory assessment/history and usage, with `late_result:true`, but cannot change status/intake/manual marker/decision/points. A result for an older evidence revision is historical only and cannot replace current assessment. Final claims never reopen through AI or citizen actions. There is no officer-to-officer final reversal operation in this work item.

### Upload and attachment (HTTP)

**ASOR-CT03.** `POST /api/media/upload`: citizen credential required; multipart/form-data with exactly one `media_file`. Success 201 `{media_id,filename,resource_name,file_size,sha256_hash,uploaded_at,is_duplicate:false}`; own same-content **unattached** upload replay returns 200 same metadata with `is_duplicate:true,duplicate_reason:"Previously uploaded by you"`. The duplicate flag concerns that citizen's upload, not global submission history. No foreign citizen's ID/hash/existence is disclosed. A same-content upload already attached to any claim returns a new owned upload handle (201); internal byte deduplication is invisible. Handles never reassign an existing attachment. Upload alone creates no report/job/provider call.

Preserve active route's media envelope: JPEG (`image/jpeg`, alias `image/jpg` normalized to JPEG), PNG; MP4 (`video/mp4`), QuickTime (`video/quicktime`), AVI (`video/x-msvideo`); 1–10,485,760 bytes inclusive **per file**. Declared MIME and decoded container must agree; extension alone is insufficient. Image/video must decode with positive dimensions; video must have a decodable visual stream with positive finite duration. No new minimum resolution, blur threshold, maximum duration, frame-rate, pixel-count or codec quality rejection is introduced. An accepted video whose codec/provider processing later fails is an AI technical outcome, not claim rejection. No audio-only, GIF, HEIC, arbitrary URL or filesystem-path upload is accepted. This preserves MIME scope/10 MiB rather than importing inactive `media.py`'s 25 MiB/45-second constants. Mixed image/video submissions are supported.

Preserve `filename` as original client display text only, never a path or URL segment. Missing/empty filename uses a generated display filename. New `resource_name` is a unique server-assigned basename containing only ASCII letters/digits, hyphen, underscore and a format-appropriate extension; returned evidence URLs use resource_name, never filename. Clients use the supplied media.url rather than construct URLs from display text; upload handles use media_id for attachment. Own-unattached dedup returns the original handle's display filename/resource_name. Neither separators, drive paths, traversal nor URL values can select local files. Failed upload leaves no visible media handle, report or AI job; successful orphan upload remains private and attachable by its owner. Automatic deletion/retention expiry is not added.

Failures: 401 credential; 400 `INVALID_MULTIPART`/`INVALID_MEDIA`/`UNSUPPORTED_MEDIA_TYPE`/`MEDIA_TOO_LARGE`; 500 `INTERNAL_ERROR`, 503 `STORAGE_UNAVAILABLE`. Missing file, zero bytes, more than one part named file, wrong field name, malformed multipart => 400. Unknown multipart nonfile fields are ignored. No provider call occurs on invalid upload.

**ASOR-CT04.** `POST /api/reports`: required JSON fields `violation_type`, `vehicle_number`, `location`, and exactly one of `media_id` (legacy string) or `media_ids` (nonempty array of distinct strings). Categories are exact case-sensitive `helmet|triple-riding|red-light`; number/location are nonblank strings stored as supplied, with no new plate-format/geography validation. Array order is submitted order. No application attachment-count/aggregate-byte cap is imposed; each file retains the existing 10 MiB boundary. Duplicate IDs within the array => 400. Supplying both aliases, even equivalent, => 400 `INVALID_INPUT`. Null/missing/empty array or whitespace-only string => 400. All handles must exist, belong to authenticated citizen and be unattached. Nonexistent 404 `MEDIA_NOT_FOUND`; foreign 403 `FORBIDDEN`; already attached 409 `MEDIA_ALREADY_ATTACHED`. Entire operation is atomic: no partial claim/attachment/job, and unchanged orphan handles after failure.

Success 201 retains `{report_id,status:"awaiting-review",violation_type,created_at,citizen_id}` plus Summary. `vehicle_number`, category, original location and citizen ID are immutable after submission in this work item. `media_ids` append only through the documented recovery operations. Unknown fields, including caller `status`, `points`, `citizen_id`, `ai`, are ignored and never override server values, preserving baseline dict-input compatibility. This is not an update/replace endpoint. Optional `Idempotency-Key` follows Contract-Wide Rules; no key preserves separate submissions and attachment-conflict protection.

**ASOR-CT05.** Private evidence reads: `GET /api/media/{media_id}/{filename}` requires the owning citizen credential; any authenticated officer can instead use the preserved `GET /api/authority/reports/{report_id}/media/{filename}`. The existing path parameter name filename denotes **resource_name**, not display filename, for new uploads. Officer media keeps existing Bearer-header-first or `token` query credential fallback solely for current embedded-media compatibility. New UI may fetch bytes with its current identity and display a local object URL; it must not make private media public. No provider key ever appears in URLs. Route basename must match resource_name in the server-returned URL; not a path selector. Success 200 original media type; missing handle/association/file or wrong basename 404 `MEDIA_NOT_FOUND`; unauthenticated 401; wrong citizen 403. Legacy attached media inherits report owner; legacy unattached media with no provable owner is inaccessible/unattachable (404) rather than assigned to the next caller. Existing legacy URL basename remains accepted only when it is a plain basename matching associated metadata and resolves to an existing file inside the configured media-store root. All new/legacy serving, AI reads and ZIP reads resolve stored paths and verify containment in that root; an arbitrary stored absolute path is not authorization. Unsafe/traversing legacy records are inaccessible (404 for media) and produce safe 500 export failure rather than reading outside storage. ZIP entry names use `media/{resource_name}`, never raw display filename or a stored path, while manifest display metadata is retained. Officers may read every claim in every AI/workflow stage. Authenticated evidence responses are private/no-store, with no public shared cache. Serving/export never requests an arbitrary remote URL or arbitrary path.

### Citizen reports and recovery (HTTP)

`GET /api/reports?page=1&page_size=20` remains citizen-own-only, 200 `{reports,total_count,page,page_size}`; ordering created_at descending, ID ascending to resolve ties. Page/page_size positive integers, no new upper cap. Invalid integer syntax is existing FastAPI 422 `detail` validation; less than 1 is 400 `INVALID_PAGINATION`. Empty/past-last page is `reports:[]` with real total. Items retain `id,status,violation_type,vehicle_number,location,created_at,updated_at,provisional_points` plus Summary.

`GET /api/reports/{report_id}` remains 200 owned detail retaining `id,citizen_id,status,violation_type,location,provisional_points,created_at,updated_at,timeline,media`; adds `vehicle_number` and Detail. Unknown report 404, other citizen 403, missing/invalid identity 401. Citizen receives the accepted AI explanation/score/history, not raw provider responses, credentials, file paths or private operational diagnostics.

**ASOR-CT06.** `POST /api/reports/{report_id}/manual-review`: own citizen credential; JSON object with optional `reason` (null/absent/blank => null; otherwise string). Allowed only effective AI screen-out and not officer-final. Success 200 `{report_id,status:"awaiting-review",manual_review_event:{id,old_status:"ai-screened-out",new_status:"awaiting-review",created_at,reason}}` plus Summary. Preserves claim ID, every attachment, original submission, AI explanation and history; marks manual queue; stops further automatic screen-out for that evidence revision. Identical request repeated while marker already true returns 200 original event/marker without new event/revision/job, even if later officer-finalized; different reason after first request => 409 `ACTION_CONFLICT`. On a never-screened-out or unrequested other state => 409 `INVALID_STATE`. A finalization race is serialized: if officer committed first without an existing manual-review event, 409; if manual review first, officer may still decide. No separate appeal record, no automatic AI rerun.

**ASOR-CT07.** `POST /api/reports/{report_id}/resubmit`: own citizen; requires nonblank `clarification_text` and exactly one `new_media_id` or `new_media_ids` (same nonempty/distinct/owned/unattached rules as intake). Only effective AI-screened-out claim; not officer-finalized. Appends new evidence to the same claim, preserves explanation/history, starts one new revision/job and returns 200 `{report_id,status:"resubmitted",new_media_ids,resubmission_event:{id,old_status:"ai-screened-out",new_status:"resubmitted",created_at,reason}}` plus Summary. `reason` is submitted clarification text. The new job considers **all** evidence, not just new attachments. The previous job's attempts remain; each evidence revision has its own three-attempt bound. This deliberate evidence-changing action is not a reset/retry button.

Existing `POST /api/reports/{report_id}/clarification` keeps required `clarification_text` + singular `new_media_id`, accepts plural `new_media_ids` with the same exclusivity rules, and is allowed only `awaiting-citizen-info`. It now actually appends/associates the owned evidence and stores the citizen text. Returns 200 retained `{report_id,status:"resubmitted",new_media_id,clarification_event:{old_status:"awaiting-citizen-info",new_status:"resubmitted",created_at}}` plus `new_media_ids` and Summary; `new_media_id` is first ID for plural input. Adds event ID/reason to clarification_event. Final/other state 409; attachment errors as intake. New job is advisory; prior officer workflow authority prevents an automatic screen-out on that clarification revision. No final decision is erased.

Resubmit/clarification accept optional `expected_revision` positive integer. If supplied, mismatch => 409 `STALE_REVISION`; omission uses atomic current-state eligibility, preserving existing clients. Response loss is replay-safe with optional Idempotency-Key; without it a repeated already-attached input yields 409, never another association/job/event.

### Officer decision (HTTP)

**ASOR-CT08.** `POST /api/authority/reports/{report_id}/decision`, officer authentication, existing JSON aliases retained: `decision_type` or `action`; `approved` maps approve, `rejected` maps reject; canonical actions `approve|reject|request-info`. Text aliases `comments` or `reason`. Supplying both action aliases is accepted only if normalized equal; both text aliases only if equal after blank-to-null conversion, otherwise 400 `INVALID_INPUT`. Action is required/nonblank string. Null/absent/blank comments/reason => null; nonstring text => 400. No new mandatory reason is imposed on legacy clients; officer UI prompts for reasons, especially reject/request-info. Optional `expected_revision` as above. Unknown/read-only request fields ignored, including points and category. No caller-set award.

Allowed from every **nonfinal workflow state**, regardless of `ai.state`, including AI-screened-out, failed AI, pending/running, resubmitted, awaiting-citizen-info and legacy open rows. This is the override operation; no separate override route. Screen-out override atomically opens intake, records the officer action, keeps AI history and assigns only human-authorized points. No AI-completion prerequisite/guard.

Success 200 retains `{report_id,status,decision_event}`; approve includes `violation_type,provisional_points`, reject includes `reason`, request-info includes no new required input. In every case add Summary and points. `decision_event` includes `{id,old_status,new_status,created_at,provisional_points,comments,reason}`; reason/comments both canonical text-or-null. Old status is actual committed prior status, not hardcoded awaiting-review. Request-info retains points (normally 0), approval assigns existing mapping once, rejection of a new/unawarded claim leaves 0. Historical stored points are not silently removed by unrelated migration; anomalous legacy points are exposed for review rather than AI-corrected.

Officer decision, points, immutable event and revision are one atomic commit. Competing different final actions or canonical text: first commit wins; loser 409 `ALREADY_FINALIZED`. Same final action and canonical text is a semantic replay, returning 200 original event/outcome without new event/points/revision (even another authorized officer); original recorded actor stays unchanged. Same request-info/text repeated while already awaiting-citizen-info returns original 200; a different request-info/text may be a new officer action. If expected_revision is provided, stale check is performed after exact idempotency/semantic replay but before a new mutation. Citizen/AI updates cannot overwrite finalization. No lock may require an officer to wait for provider completion.

Failures: 401 `UNAUTHENTICATED`; unknown report 404 `REPORT_NOT_FOUND`; malformed JSON/object/action/text/revision 400; conflicting aliases 400; stale/competing/final state 409; storage unavailable 503; unexpected failure 500. Request-info is permitted before/after AI completion; a late result remains advisory without changing requested-information status.

### Officer queue and dashboard (HTTP)

Existing `GET /api/authority/reports?page=1&page_size=10&status=...` stays 200 `{reports,total_count,page,page_size,total_pages}` and adds `counts,as_of,view`. Existing row keys `id,citizen_id,status,violation_type,vehicle_number,location,created_at,media_count` retained plus Summary. FIFO `created_at` ascending, ID ascending ties. All officers see same set. Existing default with no view/status remains awaiting-review or resubmitted; newly created pending/running AI claims already have awaiting-review and appear immediately. `status` exact case-sensitive current/legacy status match; no fuzzy text or citizen identity filter. New `view` enum below is optional; if both provided, membership is intersection. Unknown view => 400 `INVALID_FILTER`; empty `status` means omitted for existing compatibility. Unknown nonempty status => empty results, not category inference. Invalid pagination as citizen list; total_pages ceiling(total/page_size), zero for empty.

**ASOR-CT09.** New `GET /api/authority/dashboard?view=all-open&page=1&page_size=10` uses the same response, officer auth, filters/order/pagination; default all-open, not the old queue default. It accepts optional status intersection. Every response's counts describe the entire unfiltered officer-visible corpus from the same committed snapshot as its rows/total; pagination/filter changes do not redefine card counts. `as_of` is UTC snapshot timestamp, not a promise that later independent requests are identical.

**ASOR-CT11.** A validated assessment contains exactly these server-facing fields (all required):

Confidence labels do not imply that 0 means irrelevance or that 100 authorizes a violation finding. For irrelevant evidence violation score still describes self-assessed suspected violation (normally low); never invent null/0 scores when no valid result exists. Pending/failed/legacy has `assessment:null`, so UI says unavailable. Law notes on irrelevant evidence use category reference with `not-established`, explain absent traffic context, and do not allege a violation.

**ASOR-CT12.** Whole-submission decision policy is qualitative, not a numeric gate:

1. Only evidence with **every attachment clearly irrelevant**, no contradictory relevant content, all attachments assessed and no uncertainty/incomplete decoding may produce `relevance:irrelevant` and `screen-out-irrelevant`. Explanation identifies what was actually seen and why unrelated to traffic. Original citizen-selected category/plate text alone does not turn unrelated visual evidence into a proven violation; if it creates unresolved contextual doubt, send needs-human-judgment.
2. Any relevant traffic evidence prevents screen-out, even with unrelated attachments. Blur, darkness, occlusion, a missing event moment, absence of a visible violation, missing legal context, low confidence or provider inability is never irrelevance.
3. `recommend-approve` means observed facts suggest the reported category under the reviewed rule, subject to limitations. `recommend-reject` means relevant evidence does not support that reported suspected violation. Both go to officers; uncertain applicability/evidence uses needs-human-judgment. No automatic legal determination, point/fine calculation, identity assertion or accusation beyond the reported category.
4. Contract-consistency validation controls automation: a model proposing screen-out with any relevant/uncertain attachment, missing evidence, internally inconsistent explanation or technical gap is not authorized to screen out. Structurally valid uncertainty is displayed with needs-human-judgment; malformed/inconsistent output follows technical failure below. Model instructions inside evidence/OCR/citizen text have no authority over policy, credentials, tools, legal catalog or decisions.

| Representative input | Required route / explanation |
| --- | --- |
| Clear food photo and indoor nontraffic clip, neither claiming observable traffic context | May screen out with specific observed irrelevance. |
| Road/motorcycle evidence, visible compliant helmet or no apparent violation | Officer referral; recommendation may be reject with reviewed rule notes. |
| Blurry road-like image, unlit/occluded rider or red-signal still without crossing sequence | Needs human judgment; never auto screen-out. |
| Irrelevant indoor image plus relevant road video | Officer referral based on combined evidence; irrelevant attachment cannot veto. |
| Relevant evidence concerning another category / location or apparent plate mismatch | Officer judgment with limitation; no new category, no automatic irrelevance inference. |
| One apparently irrelevant image plus unreadable video or missing frames | Technical/uncertain referral; never assume all evidence irrelevant. |

**ASOR-CT13.** Output validation: one structured object, no markdown wrapper/freetext substitute; required enum/field/type/range/citation/media checks above; unknown model fields are not public and cannot grant authority. Missing/blank explanation, absent scores, extra/missing attachment entries, invented reference IDs/URLs or numeric violations => terminal technical `INVALID_MODEL_OUTPUT` (one attempt, no automatic repair call). Provider safety block/refusal => `MODEL_OUTPUT_UNAVAILABLE`; timeout/provider failure distinct. No partial assessment accepted, no fabricated observations/citations/scores, no silent normalization that changes model meaning. Public assessment null, job failed, officer referral remains immediately available. A valid assessment that explicitly cannot establish a violation is **completed/uncertain**, not technical failure. Any provider response usage, including invalid output, is still recorded for cost.

### Durable processing and dependency outcomes

**ASOR-CT15.** One durable job per accepted evidence revision. Report acceptance never awaits provider completion. Current jobs transition pending → running → completed; transient failure running → retry-wait → running; terminal/exhausted failure → failed. Finalization before a pending/retry job is dispatched cancels it (`cancelled`, reason `OFFICER_FINALIZED`), without a provider call. An already-dispatched job may finish as advisory late output; it must not initiate more attempts after officer finalization. Cancellation does not hide prior attempts/usage. No new job is scheduled for manual-review request or repeated HTTP action. Legacy no-job claims stay not-requested and immediately officer-reviewable.

Attempt count increments durably **before** potentially billable provider dispatch, and is never decremented. Each attempt includes all provider file-upload/preparation/inference work needed for that revision, under one overall deadline; nested SDK retries or automatic model repair must not multiply dispatches. At most one inference dispatch per attempt and at most **three total attempts per job**, including interrupted/uncertain attempts. File-read/configuration failures before dispatch may end failed with zero attempts; no fake successful assessment. Restart pending job remains pending/count unchanged; restart in-flight attempt becomes `INTERRUPTED` and consumed, with unknown billing if provider outcome unavailable; retry only if eligible and fewer than three consumed attempts. No exactly-once provider billing guarantee is claimed.

| Failure class | Observable code | Retry rule |
| --- | --- | --- |
| Connection failure/reset, provider 408/429/500/502/503/504, local attempt deadline, interrupted in-flight attempt | `PROVIDER_TRANSIENT`, `ATTEMPT_TIMEOUT`, `INTERRUPTED` | Retry within three total; 429 Retry-After respected as below. |
| Invalid/missing API key, provider 401/403, unavailable/unsupported model or request 400/404, unsupported provider processing | `PROVIDER_CONFIGURATION`, `PROVIDER_REQUEST_REJECTED` | Terminal; officer review, no silent model fallback. |
| Invalid/blocked/unavailable output | `INVALID_MODEL_OUTPUT`, `MODEL_OUTPUT_UNAVAILABLE` | Terminal, no repair retry. |
| Missing/unreadable evidence, local preparation error | `EVIDENCE_UNAVAILABLE`, `PROCESSING_ERROR` | Terminal, no claim rejection. |
| Retryable failure on attempt 3 | `ATTEMPTS_EXHAUSTED` with last-cause code in attempts | Failed, never a fourth attempt/restart reset. |

Durable commit/lease ownership and evidence-revision checks prevent concurrent duplicate accepted results, stale workers or recovered work from publishing twice. Any obsolete completion is recorded as superseded operational outcome, not effective screen-out/current assessment. No external exactly-once delivery claim. Local storage failure while accepting a report/mutation gives 503 with no advertised successful commit; ambiguous network response is resolved by idempotency replay/read. Once a job is committed, failure to reach the selected provider does not lose the claim/evidence or block officer actions. No in-memory-only queue acceptance.

## Contract-Wide Rules

- **Boundary scope:** rules in this section govern changed feature JSON/multipart routes above, not untouched auth/control/public/export contracts. JSON body must be object; malformed/unreadable JSON, array/scalar/null body, wrong field type => 400 `INVALID_INPUT` (even though some old dict/framework paths differed). Unsupported JSON content type => 415 `UNSUPPORTED_CONTENT_TYPE`. Empty/missing required body => 400. Strings are not coerced from numbers/booleans. Required strings reject missing/null/empty/whitespace-only; otherwise original text retained. Optional reason/comments blank/null/absent normalize to null; other optional null behaves omitted, except alias exclusivity still rejects both supplied media aliases. Unknown fields/read-only fields ignored and never stored as authority. New server fields are not client-settable.
- **Identifiers:** new report/media/job/event IDs are 16 lowercase hex characters. HTTP path/attachment IDs are treated as opaque nonblank strings for legacy compatibility; a nonmatching arbitrary identifier returns 404, not a new syntax prohibition. Absent required ID/empty path is ordinary route-not-found; blank body IDs 400. Ownership checks precede content disclosure. Detail own-citizen report distinction remains unknown 404 versus other owner's 403. Officer credential is required before report lookup. Filename matching is exact, case-sensitive metadata lookup after safe URL decoding, never filesystem interpretation.
- **Errors:** changed routes use `{error:string,detail:string,code:string}`. error/detail contain same safe human-readable message, may change wording; code and HTTP status are normative. Defaults: 400 `INVALID_INPUT`; 401 `UNAUTHENTICATED`; 403 `FORBIDDEN`; 404 `REPORT_NOT_FOUND`/`MEDIA_NOT_FOUND`; 409 named conflict; 500 `INTERNAL_ERROR`; 503 `STORAGE_UNAVAILABLE`. Route-specific media/filter/parse codes take precedence where defined. No raw exception/provider output. Existing framework 404/405 and integer-query 422 `detail` shape remain for unmatched routes/methods and malformed integer query. No invented success on error. Client handles error or detail, so existing browser handlers remain compatible.
- **Idempotency:** optional `Idempotency-Key` on create, clarification, resubmit and decision: nonblank printable ASCII 1–128 characters; null header impossible, blank/invalid => 400. Scope authenticated principal + method + route + key. First successful committed operation stores normalized request and response durably for the life of the local data; same key/request replays original status/body without new report/evidence/job/event/points. Same key/different normalized request => 409 `IDEMPOTENCY_CONFLICT`; in-flight same key => 409 `REQUEST_IN_PROGRESS`, safe to retry same key. Failed uncommitted validation/auth request does not reserve key. Fingerprint uses canonical actions/aliases, normalized optional text and original ordered media IDs; ignores unknown fields. Replay authenticates/access-checks first. Exact final-action/manual-review natural replay rules additionally apply without a key. No blanket exactly-once promise for requests without keys; attachment/terminal guards still prevent duplicate effects.
- **Concurrency:** mutations serialize eligibility/revision/attachment checks with commit. If more than one condition conflicts, authentication/ownership then exact replay, terminal conflicting officer action, expected_revision, other workflow eligibility, then attachment conflict governs. Nonfinal state races can yield 409 `STALE_REVISION` or `INVALID_STATE` as appropriate; terminal competing officer action uses `ALREADY_FINALIZED` even with a stale expected_revision. AI only updates its job/assessment and may screen out only if its snapshotted workflow/evidence version is still automation-eligible. It does not increment user workflow revision or make an otherwise valid expected_revision stale merely by progressing. Successful mutation returns its own committed snapshot; a later read may show later AI/progress changes.
- **Times/numbers:** new timestamps UTC RFC3339 with `Z`; legacy timestamps retained when read, parsed for ordering where valid. New IDs break equal-time ties; unparseable legacy times sort by stored text consistently, remain visibly legacy. Revision/count/points/time/confidence are integers as specified, no floats/NaN/Infinity. Monetary arithmetic as Usage; points mapping not rounded or multiplied by confidence. No cursor/sort/search semantics are added. Lists return arrays, never null; totals count reports not attachments/jobs.
- **Versioning:** in-place compatible HTTP routes plus explicit additive versioned policy/legal/prompt records; no new `/v2` surface or public RPC/messages. New statuses/errors/owned media protections/action semantics are explicit compatibility deltas submitted for review. Consumers must not equate unknown/missing AI result with rejection or human approval.
